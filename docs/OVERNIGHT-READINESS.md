## Deliberate blockers

These are safe constraints, not defects to bypass overnight:

1. `LIVE_MODE_ENABLED` is `false`; the run API and worker are dry-run-only.
2. The typed action registry contains Meta actions only. Shopify, HubSpot, and Klaviyo execution
   verbs in seven mutation specs return `not_implemented` instead of pretending to be actionable.
3. `meta.campaign.create_from_brief` is dry-run-only. Its shaped create requests use PAUSED status;
   neither D02-W02 nor D02-W08 is an activation path.
4. Live readers exist for Shopify, Klaviyo, GA4, Meta, and HubSpot. Google Ads is fixture-only, and
   Instagram, TikTok, LinkedIn, YouTube, Search Console, Gmail, Gorgias, web research, LLM search,
   and calendar do not yet have worker readers. Skills that require them must wait for an n8n/read
   adapter or attributed founder-supplied material.
5. A platform connection, saved webhook URL, successful fixture call, scheduled cadence, HTTP 2xx,
   or generated artifact is not execution proof.
6. The four new dated migrations change repository state only until they are applied and read back
   on the intended Supabase project.
7. Live graduation still requires a fresh destination-state check when an approval resumes, a
   separate provider readback after Meta writes, and an atomic cross-worker reservation for action
   spend. Those paths remain unreachable while live actions are disabled.
8. Approval and artifact state transitions reject stale concurrent decisions, but the status,
   taste event, receipt, and run transition are still separate writes. A process failure between
   those writes can leave an incomplete audit trail; make each decision a database transaction
   before enabling live actions.

## AVGAR first-customer test sequence

Keep the first pass reversible and observable:

1. Freeze and review the exact branch commit. Confirm no secrets or customer data are in the diff.
2. Apply the Supabase migrations to the intended project, then prove account membership and
   two-account isolation. Specifically test the similarity RPCs as anon, authenticated, and service
   role after the migration.
3. Provision AVGAR through client-owned accounts/OAuth. Verify account identity, property/store/ad
   account ids, scopes, token storage, and one fresh read per source before calling a connector ready.
4. Keep every routine in dry-run/draft mode. Start with one launch-wave routine whose inputs can be
   checked manually, then compare its artifact line-by-line with the source data and AVGAR voice.
5. Add one n8n routine only after the built-in version has a known expected artifact. Verify signed
   request, account/run scopes, source reads, returned artifact, and failover separately.
6. Review artifacts in the founder loop: approve, edit, hold, and explain. Confirm artifact approval
   cannot authorize a destination mutation.
7. Exercise one mutation routine as proposal-only. The expected result is an exact dry-run preview
   or an explicit blocker, never a provider-side change.
8. Retain receipts for every read, draft, approval, blocker, and comparison. Mark the first wave
   `PASS`, `PARTIAL`, or `BLOCKED` from those receipts before onboarding a second customer.

## Graduation criteria for one routine

A routine is first-customer-testable when all of the following are true for one isolated AVGAR
account:

- its source identity and freshness are proven;
- its skill either produces a useful, source-grounded artifact or asks for the precise missing
  material;
- a second account cannot read or alter its runs, artifacts, approvals, receipts, or credentials;
- every consequential step is understandable before approval;
- holding or denying causes no destination change;
- a dry-run mutation names the exact target, parameters, risks, spend, rollback, and blockers;
- any claim of provider success includes response plus fresh destination readback;
- failure and retry cannot duplicate an action;
- the founder can tell in seconds what happened, what did not happen, and what Unc needs next.

Until those conditions have customer-scoped receipts, the honest status is **private-beta
candidate**, not fully working automation.
