# Keyword shadow completion — original run, one atomic result

5 September 2026, approximately 08:23 UTC. Source/rollback verification only; not deployed or customer-accepted.

## Actual update

Normal keyword success and interrupted-run recovery now share one completion path. The engine no longer writes a keyword shadow artifact, its receipts and terminal run status separately. This is the customer-record continuation of [Batch 20's private archive recovery](KEYWORD-RECOVERY-2026-09-05.md); it does not replace the independent execution reader or Nguyen's frozen contract.

1. Before dispatch, the engine persists its original full specification/context and next-node position with `awaiting: keyword_shadow`. The ordinary async callback accepts only `awaiting: n8n`; it cannot inject an unverified result here. Missing atomic-completion support refuses before dispatch.
2. The existing bridge uses one-use admission, checkpoints the response, independently verifies the saved execution and stores its verified result in the original permit.
3. Completion reads that durable verified result, not an in-flight callback payload. It runs **only the original post-producer draft review gates and final receipt** into an isolated staging store. No reader/model/provider/executor adapters are available. Spec fingerprint, run/version/account/generation and original context must agree; a second producer or an executable continuation is rejected.
4. `commit_keyword_shadow_completion` locks the current account, original permit/run and original owner's membership. It compares the full captured snapshot/spec and the exact artifact against the verified ledger. In one transaction it inserts the draft artifact and linked execution/review/final receipts, completes the original run and records one immutable completion key.
5. A duplicate call or a lost response returns the first committed artifact/receipt identities. A mid-write failure rolls everything back. The engine never clears its continuation or overwrites `done` with `failed` merely because completion's response was lost. An uncertain result stays pending reconciliation, not an automatic new provider request.

The original review preview and final receipt wording/measurement window are generated by the existing engine; this is not a second hardcoded routine with shortened semantics. Reviews remain draft previews, not live approvals or executed actions. Existing command reconciliation can observe the completed original run; channel sending remains separately disabled/gated.

The completion planning clock is fixed for the transaction packet. Source execution/fetch times remain in the verified receipt; completion time is not source freshness. The evidence list reserves room for the execution reference so revalidation cannot drop it at the 40-entry limit.

## Recovery operator

With compiled worker and privately injected approved server configuration:

`scripts/reconcile-keyword-shadow.mjs --permit <original-permit-id> --original-generation <original-generation> --persist-verified-archive`

This still performs **archive-only** recovery by default. Add `--complete-original-run` to request the current-context atomic artifact/receipt/run completion. It logs identifiers/status only. A paused/reset account or changed original owner cannot receive a fresh customer projection; its private archived execution evidence is retained. A removed registration does not erase the already-authorized result, nor does completion re-enable that registration.

This operator command has **not** been run on a live provider execution. The new migration and supported execution-reader access are prerequisites. It is not a cron, public route or new n8n workflow. No purchases, credentials, publishing, messaging or ad mutations are authorized by it.
